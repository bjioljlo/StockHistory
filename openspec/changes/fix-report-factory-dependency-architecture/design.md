## Context

目前架構問題：
```
IGetExternalData (介面)
    ↑
TGetExternalData (真正實作)
    ↑
ExternalDataFactory (工廠類別 - 只有 Get_instance() 方法)
```

整個系統超過 27 個地方直接把 `ExternalDataFactory` 物件當成 `IGetExternalData` 注入，導致執行階段隨機出現方法不存在的錯誤。

## Goals / Non-Goals

**Goals:**
✅ 解決所有「找不到方法」的執行階段錯誤
✅ 100% 向後相容，不需要修改任何其他程式碼
✅ 保留既有的工廠功能
✅ 最小程式碼變更，只修改 ExternalDataFactory 一個檔案

**Non-Goals:**
❌ 不修改任何其他模組
❌ 不改變任何既有行為
❌ 不重構整個系統的依賴注入架構
❌ 不中斷現有功能

## Decisions

### 架構選擇：工廠 + 代理 混合模式

```
┌───────────────────────────────────┐
│   ExternalDataFactory             │
│   ✅ 實作 IGetExternalData 介面   │
│   ✅ 內部快取真正的 TGetExternalData 實例 │
│   ✅ 所有方法自動轉送到真正的實例 │
└─────────────┬─────────────────────┘
              │
              ▼
    TGetExternalData (真正實作)
```

✅ 為什麼選擇這個設計？
- 不需要修改任何現有程式碼
- 對整個系統完全透明
- 保留了原有的工廠功能
- 解決了根本問題
- 只有一個檔案需要修改

### 替代方案比較

| 方案 | 優點 | 缺點 |
|------|------|------|
| 現在的混合模式 | ✅ 零變更其他程式碼 ✅ 立即解決問題 | 架構上不是最純粹 |
| 修改所有注入點 | 架構乾淨 | ❌ 需要修改超過 27 個地方 ❌ 高風險 ❌ 耗時 |
| 重新設計依賴注入 | 長期最好 | ❌ 整個系統重構 ❌ 非常高風險 |

## Risks / Trade-offs

[風險] 可能有某些介面方法沒有被轉送 → 使用 `__getattr__` 自動轉送所有方法

[風險] 執行效能影響 → 只有第一次呼叫會建立實例，之後都是直接轉送，效能影響可以忽略

[風險] 除錯變得比較複雜 → 保留原始 Get_instance() 方法，需要除錯時可以直接取得真正的實例
